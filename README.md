# RewardGuard — a robustness verifier for LLM-as-a-Judge

> Your reward model is fooled by a colon. RewardGuard isn't.

**The user & the bottleneck.** Frontier models are trained with RL, and RL needs a *reward signal that can't be gamed*. The teams building those signals — AI labs, RL-environment engineers, eval companies like micro1 — have a problem: **LLM-as-a-judge reward models are trivially fooled.** Recent work ([*One Token to Fool LLM-as-a-Judge*, 2026](https://arxiv.org/abs/2507.08794)) shows that feeding a judge just `":"` or `"Let's solve this step by step"` — with **no actual answer** — earns a *passing* reward 35–90% of the time across GPT-4o, Claude-4, and Qwen. In a real RLVR run the policy learned to exploit this and collapsed to sub-30-token garbage that still scored well. When your verifier is broken, your training run is broken.

**What RewardGuard does.** It's an **agentic verifier** that decides pass/fail for a (prompt, reference, candidate-answer) triple and *refuses to be fooled* by content-free "master-key" inputs. It does this without fine-tuning a reward model — instead it orchestrates a short reasoning pipeline:

1. **Rubric decomposition** — turn the reference/criteria into concrete, checkable points.
2. **Substance check** — does the candidate actually contain substantive content addressing those points, grounded against the reference?
3. **Adversarial false-positive gate** — explicitly test whether the candidate is just an opener / punctuation / keyword-stuffing with no real content; if so, **REJECT** regardless of surface plausibility.

This is the same self-verification + false-positive-gate pattern proven in my prior projects (Alma Agent, Lexica), applied to reward-model robustness.

## Quick start

```bash
cp .env.example .env          # add ANTHROPIC_API_KEY or OPENAI_API_KEY for real runs
pip install -r requirements.txt

# 1. Generate the deterministic master-key attack set
python -m rewardguard.attacks --out data/attacks.jsonl

# 2. Run the evaluation (baseline vs RewardGuard) on the same cases
#    --mock runs with NO keys and canned behavior so you can see the shape first
python -m evals.run_eval --mock
python -m evals.run_eval            # real LLM run (needs a key)

# 3. Launch the Judge-vs-Verifier demo page
python -m rewardguard.server        # then open http://localhost:8000
```

## Reproduction guide

- **Clean environment:** Python 3.11+. `pip install -r requirements.txt`.
- **Data:** `evals/gold.jsonl` (genuine pass/fail cases) + `data/attacks.jsonl` (generated by `rewardguard.attacks`). No private data — all synthetic or public.
- **Baseline:** `python -m evals.run_eval --judge baseline`
- **Solution:** `python -m evals.run_eval --judge rewardguard`
- **Both + comparison:** `python -m evals.run_eval` (default runs both, writes `evals/results/latest.json`).
- **Expected output:** a per-category table (attacks vs genuine) with false-positive rate and agreement, and a written JSON report.
- **Model / cost / runtime:** judge model set by `JUDGE_MODEL` (default noted in `.env.example`); a full run over ~500 attacks + ~20 gold cases is a few cents and ~2–4 minutes.
